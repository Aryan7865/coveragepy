Generated servers and clients declare a separate response type for every operation, even when operations refer to the same response from the spec's `responses` section. An API whose operations all return a common error response ends up with one unrelated type per operation (`GetFooForbidden`, `GetBarForbidden`, ...), so callers cannot handle that response with a single piece of code.

When two or more operations generated into the same package refer to the same named response under the same status code, the generated server and client should declare a single type for it in that package, used by all of these operations: their client readers, their client methods and their strict responders. The default response counts as its own status code and is never merged with an explicit one, and a named response used under several status codes, whether or not it carries an `x-go-name`, gets a separate type for each code. A named response is identified by where it is defined, so responses with the same key or the same `x-go-name` defined in different places are not merged, and references made from path items defined in other documents count too. Operations in different packages, such as different tags, each get their own declaration and must not depend on one another. Inline responses, and named responses used by a single operation of a package, keep their current operation-specific types.

Which operations share a response depends on the whole spec, not on the operations selected for a run: generating a subset of the operations, or adding operations one at a time with `swagger generate operation`, must leave each package compiling and give the same types as generating everything at once. Generated code must compile whatever the names of shared responses, including names that collide with types, constructors, parameters or bodies already generated in the package, and generation must stay deterministic, also with a fully flattened spec and for the command line client.
