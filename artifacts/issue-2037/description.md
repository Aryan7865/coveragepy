Add an opt-in `[run] timestamps` setting that records when each line, and with branch coverage each arc, was first executed. A timestamp is the wall-clock time in seconds since the Unix epoch, as returned by `time.time()`, taken when the line or arc first runs; running it again never changes it, even if the data was saved or the context was switched in between. This has to work whichever measurement core is in use.

The timestamps are part of the coverage data, so they survive writing and reading the data file, `dumps()` and `loads()`, and combining. They are kept per context like the rest of the measurement, and when several contexts are queried the earliest time among them is reported. Combining data, including data whose paths are remapped, keeps the earliest time for each line and arc; data measured without timestamps combines as usual but contributes no times. Purging a file's data also removes its timestamps.

Expose them with two new `CoverageData` methods. `line_timestamps(filename)` returns a dict mapping executed line numbers to their first execution time, and also works for branch data. `arc_timestamps(filename)` returns a dict mapping executed arcs, as returned by `arcs()`, to theirs. Both return None for a file that wasn't measured, like `lines()` and `arcs()`, and anything executed without timestamps enabled has no entry.

When the data being reported has timestamps, the JSON report should include them: every file entry and every function and class region gets a `line_timestamps` object mapping each of its executed lines to an offset in seconds from when measurement started (the first `Coverage.start()`), and with branch coverage also a `branch_timestamps` list of `[from, to, offset]` entries for its executed branches. Lines and branches with no recorded time are left out. For combined data the offsets are measured from the earliest start among the combined runs. With the setting off, measurement and reports stay exactly as they are today.
